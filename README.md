# AOI 过杀复判 · Pseudo-Defect Recheck

> 工业视觉质检里的「第二双眼睛」：不重新检一遍缺陷，而是判断 AOI 已经报出的 NG **到底是真缺陷还是误报**。

## 为什么这不是一个"缺陷检测"项目

产线上的 AOI 用传统 CV（灰度阈值、对比度、边缘规则）挑缺陷。这类方法在**召回**上够用，代价是**精度**很差：光照不均、侧边反光、料带偏移、镜头脏污，都会让好产品被判成 NG。

于是产线出现一个隐性成本：AOI 报出的 NG 里混着大量假 NG，必须靠人工复核逐张看。**缺陷检测任务在这里已经做完了，缺的是一个裁决环节。**

```
 产线           AOI（传统CV）        人工复核            本服务
┌──────┐      ┌──────────┐      ┌──────────┐      ┌────────────┐
│ 相机  │─────▶│ 阈值规则   │─────▶│ 逐张看    │      │ 旁路判别    │
└──────┘      │ 判 NG/OK  │      │ 真/假 NG  │      │ 真NG / 伪NG │
              └──────────┘      └──────────┘      └────────────┘
                     │                                    ▲
                     └──── 缺陷 crop + 元数据 ─────────────┘
                          （只读，不改 AOI 代码）
```

## 三个刻意的设计选择

### 1. 旁路，不侵入

不修改客户既有的 C++ AOI 代码。原因不是技术洁癖，是**交付风险**：改产线代码意味着故障责任不清、回滚成本高、客户产线停机时间不可控。旁路方案的代价是多一次 IO，换来的是「上线失败可以无声退回原流程」。

### 2. 判真伪，不判缺陷

如果目标定成「检出缺陷」，就变成和 AOI 抢活，验收标准也说不清。定成「对已报 NG 做二分类」，验收标准立刻变成可量化的一句话：**这批 NG 里有多少真缺陷被漏掉**。

### 3. 阈值按代价定，不按 0.5 定

漏检（真缺陷判成伪）会让缺陷件流出，过杀（伪缺陷判成真）只是白派一次人工复核。两者代价差一到两个数量级，所以阈值不能取 0.5，要按**期望代价最小**求解：

```
E[cost] = C_fn · FN(τ) + C_fp · FP(τ)
τ* = argmin E[cost]
```

`src/evaluate.py` 会直接画出 cost-vs-threshold 曲线，τ* 由数据决定，而不是拍脑袋。

## 快速开始

```bash
python -m venv .venv && .venv/Scripts/activate      # Windows
pip install -r requirements.txt

# 1. 构建数据集（ELPV 公开数据 + 合成伪缺陷）
python data/build_dataset.py --raw data/raw/elpv-dataset-master --out data/processed

# 2. 训练（CPU 可跑，默认 320px / 30 epoch）
python src/train.py --config configs/default.yaml

# 3. 评估：混淆矩阵 / PR 曲线 / 代价敏感阈值扫描
python src/evaluate.py --config configs/default.yaml

# 4. 起服务（旁路接口）
uvicorn src.serve:app --port 8000
curl -X POST localhost:8000/recheck -F "file=@samples/cell_001.png"
```

## 关于数据：这是同构重建，不是原始数据

原始客户数据受保密约束无法带走。本仓库用 **ELPV 公开数据集**（2624 张 300×300 光伏电池片电致发光图，含功能完好/缺陷两标签）重建同构问题：

| 真实项目 | 本仓库 |
|---|---|
| AOI 输出的缺陷 crop | ELPV 单张电池片图 |
| 真 NG | ELPV 标注为 defect 的样本 |
| 被 AOI 误报的好产品 | ELPV 标注为 functional 的样本 + 现场型扰动 |
| 现场过杀诱因（光照/反光/压缩） | `data/synth_pseudo.py` 合成的退化 |

**伪缺陷是合成的**，这是本仓库最大的方法论弱点，也是我在面试里会主动交代的一点：合成样本会带来 shortcut（模型学到"扰动痕迹"而不是"像不像缺陷"）。缓解手段见 `docs/decisions.md`。

## 结果

CPU（Ryzen 7 5800H）训练 30 epoch，约 50 分钟。yolov8n-cls，320px，batch 32。

| 指标 | 值 |
|---|---|
| 测试集规模 | 438（真缺陷 146 / 伪缺陷 292，正例占比 33.3%） |
| 数据划分 | 按拍摄批次分块，train/val/test = 37/7/9 组，无同组泄漏 |
| **AUC / AP** | **0.963 / 0.947** |
| 验证集 top1（best, epoch 25） | 0.860 |
| τ=0.5：准确率 / 漏检率 / 过杀率 | 87.7% / 9.6% / 13.7% |
| **τ*=0.13（代价最优）：漏检率 / 过杀率** | **0.68% / 40.8%** |
| 朴素基线（全判伪） | 准确率 66.7%，漏检率 100% |

**怎么读这组数**：AUC 0.963 说明模型的**排序能力**是够的——真缺陷的分数普遍高于伪缺陷。剩下的问题是阈值摆在哪：τ=0.5 是"平衡点"，τ=0.13 是"宁可多派人复核也不漏检"的保守点。两者差距（漏检 9.6% → 0.68%，过杀 13.7% → 40.8%）就是这条产线要做的取舍，而取舍的依据是漏检与过杀的代价比，不是准确率。

**这个数字不能直接对标文献里的 99%**：那是同分布、闭集、真缺陷与背景差异明显的检出任务；这里是"真缺陷 vs 被误报的好产品"，两者外观重叠，本身更难。而且伪缺陷是合成的，分布与真实过杀样本有差距。

**已知瓶颈**：CPU 单张端到端约 270ms（含解码）。产线节拍若要求 <100ms，需转 ONNX + INT8 量化或降低输入分辨率。这是这套方案上产线前必须先算的账，不是精度问题。
